Создание собственного графического и физического движка с нуля — это классический обряд посвящения для любого системного программиста. Рано или поздно каждый разработчик, очарованный обещаниями языка Rust о «бесстрашной конкурентности» (fearless concurrency) и безопасности памяти без сборщика мусора, задается вопросом: *«А что, если написать компактный, модульный мультимедийный рантайм, который объединит 2D/3D рендеринг, физику частиц и твердых тел, при этом предоставив абсолютно плоский C99 ABI для бесшовного управления из Python, C или C++?»*

Именно так родился **Oxide** — открытый рантайм и графический движок на Rust (2021 Edition) с графическим бэкендом на OpenGL 4.5 Core Profile.

Но между романтической архитектурной задумкой на салфетке и реальным кодом лежит пропасть. На этом пути вас поджидают борьба с borrow checker при построении графа сцены, проклятие FFI-указателей, кошмар синхронизации деформируемых сеток мягких тел с GPU-буферами и жестокая правда об $O(N^2)$ проверках коллизий.

В этой статье я подробно, честно и без прикрас препарирую устройство Oxide (v0.3.1), разберу его ключевые подсистемы, детально проанализирую архитектурные успехи, открыто вскрою клубок серьезных инженерных недостатков и взгляну в лицо тем вызовам, с которыми сталкиваюсь я как разработчик нативного рантайма.

# Глава 1: Анатомия рантайма Oxide: от Winit и OpenGL 4.5 Core до Sparse-Set ECS и C-ABI моста

Архитектурно Oxide спроектирован по принципу строгого модульного разделения ответственности (Separation of Concerns). Ядро движка полностью изолировано от операционной системы и оконных контекстов, рендерер вынесен в независимую подсистему, а все состояние симуляции и сущностей сосредоточено в централизованном хранилище мира.

```
+---------------------------------------------------------------------------------------+
|                                  Oxide Application                                    |
|  +--------------------+   +------------------------------------+   +---------------+  |
|  |     Core Event     |   |          World (ECS Engine)        |   | Render System |  |
|  |     Loop & App     |-->|  - Entities (SlotMap<Id, ()>)      |-->| - Pipeline 3D |  |
|  |   (Winit/Glutin)   |   |  - SecondaryMap Components         |   | - Pipeline 2D |  |
|  +--------------------+   |  - Systems (Physics, Spatial, Ray) |   | - Text Engine |  |
|            |              +------------------------------------+   +---------------+  |
|            v                                                                          |
|  +---------------------------------------------------------------------------------+  |
|  |                       C99 FFI Layer (cdylib Export)                             |  |
|  |   - Opaque Pointers: *mut OxideApp, *mut OxideScene                             |  |
|  |   - Transmuted Callbacks: on_init, on_update, on_render                         |  |
|  +---------------------------------------------------------------------------------+  |
|            |                                                                          |
|            v                                                                          |
|  +---------------------------------------------------------------------------------+  |
|  |                  High-Level Language Client (Python / C / C++)                  |  |
|  |   - Python ctypes Wrapper (`bindings/python/oxide.py`)                          |  |
|  |   - C99 Headers (`include/oxide.h`)                                             |  |
|  +---------------------------------------------------------------------------------+  |
+---------------------------------------------------------------------------------------+
```

## 1.1. Оконная подсистема и жизненный цикл кадра

Любой нативный графический движок начинается с взаимодействия с дисплейным сервером ОС (Win32, Wayland, X11, Cocoa). В Oxide это реализовано в модуле `src/window/window_context.rs` и `src/core/app.rs` без использования сторонних C-монолитов вроде SDL2 или GLFW. Движок опирается на современный стек:

- `winit` (0.30) — кроссплатформенная абстракция окна и цикла событий ОС.
- `glutin` (0.32) + `glutin-winit` (0.5) — безопасное создание OpenGL-контекста и привязка к поверхности окна.
- `raw-window-handle` (0.6) — низкоуровневые дескрипторы для привязки контекста.
- `glow` (0.16) — тонкие и высокопроизводительные OpenGL-биндинги без overhead'а.

Запуск движка инкапсулирован через паттерн Строитель (`AppBuilder`):

```rust
App::build()
    .with_title("Oxide Simulation")
    .with_size(1280, 720)
    .with_vsync(true)
    .run(MySimulationHandler)?;
```

Внутри `App::run` создается `winit::event_loop::EventLoop`. Цикл кадра управляется тремя ключевыми этапами интерфейса `AppHandler`:

```rust
pub trait AppHandler {
    fn on_init(&mut self, ctx: &mut Context);
    fn on_update(&mut self, ctx: &mut Context, dt: f32);
    fn on_render(&mut self, ctx: &mut Context);
}
```

Все состояние низкоуровневого окружения инкапсулировано в структуре `Context` (`src/core/context.rs`). Контекст хранит:
1. `gl: &'a glow::Context` — сырой указатель на интерфейс функций OpenGL.
2. `width: u32`, `height: u32` — физические габариты вьюпорта.
3. `time: &'a Time` — трекер абсолютного времени, дельты кадра (`dt`) и сглаженного FPS.
4. `input: &'a InputState` — матрицу состояний клавиатуры и мыши (нажатия, отпускания, удержание, относительное смещение курсора и колесика).

Это фундаментальное решение: пользовательский код симуляции никогда не владеет оконным контекстом напрямую, а получает его во временное заимствование на время вызова соответствующей фазы кадра.

## 1.2. Архитектура мира World: выбор Sparse-Set ECS на SlotMap

Центральное хранилище данных Oxide — структура `World` (`src/ecs/world.rs`). До версии v0.3.0 движок использовал традиционное иерархическое дерево сцены (Scene Graph) с узлами `SpatialNode`. Однако в Rust графовые структуры с циклическими ссылками между предками и потомками неизбежно приводят к кошмару из `Rc<RefCell<...>>` или небезопасных указателей.

Начиная с версии v0.3.0, Oxide перешел на **Entity-Component-System (ECS)** на базе разреженных наборов (Sparse-Set pattern), используя крейт `slotmap`:

```rust
pub struct World {
    /// Реестр активных сущностей с поколенческими индексами
    pub entities: SlotMap<EntityId, ()>,

    /// Разреженные таблицы компонентов (SecondaryMap)
    pub transform: SecondaryMap<EntityId, Transform>,
    pub global_transform: SecondaryMap<EntityId, Mat4>,
    pub parent: SecondaryMap<EntityId, EntityId>,
    pub children: SecondaryMap<EntityId, Vec<EntityId>>,
    pub visible: SecondaryMap<EntityId, Visible>,
    pub collider: SecondaryMap<EntityId, Collider>,
    pub rigid_body: SecondaryMap<EntityId, RigidBody>,
    pub soft_body: SecondaryMap<EntityId, SoftBody>,
    pub mesh_3d: SecondaryMap<EntityId, Mesh3D>,
    pub surface_2d: SecondaryMap<EntityId, Surface2D>,
    pub text_2d: SecondaryMap<EntityId, Text2D>,

    pub names: SecondaryMap<EntityId, Name>,
    pub behaviors: SecondaryMap<EntityId, Box<dyn NodeBehavior>>,

    /// Глобальные ресурсы мира
    pub camera: Camera,
    pub light: Light3D,
}
```

### Как устроена идентификация сущностей?
Идентификатор `EntityId` в `slotmap` представляет собой 64-битный токен:
- **Index (32 бита):** Слот во внутреннем векторе.
- **Generation (32 бита):** Счетчик жизни слота.

Когда сущность удаляется через `world.despawn(e)`, слот освобождается, а поколение инкрементируется. Если старый клиент попытается обратиться к `e`, `SlotMap` и `SecondaryMap` мгновенно вернут `None`. Это полностью исключает фундаментальную проблему **ABA** и использование висячих указателей (use-after-free), свойственные C/C++ движкам.

### Иерархия трансформаций
Несмотря на плоскую структуру ECS, 3D-движку необходимо поддерживать логическое вложение объектов (например, турель на танке, колеса у автомобиля). В Oxide иерархия реализована через пару компонентов `parent` и `children`:

```rust
pub fn update_hierarchy_system(world: &mut World) {
    // 1. Находим все корневые сущности (у которых нет родителя)
    let roots: Vec<EntityId> = world
        .entities
        .keys()
        .filter(|&e| !world.parent.contains_key(e))
        .collect();

    // 2. Рекурсивно распространяем трансформации вниз по дереву
    for root in roots {
        let root_mat = world.transform.get(root)
            .map(|t| t.matrix())
            .unwrap_or(Mat4::IDENTITY);
        world.global_transform.insert(root, root_mat);

        propagate_transforms(world, root, &root_mat);
    }
}
```

Локальная трансформация (`Transform`) хранит вектор положения (`translation: Vec3`), кватернион вращения (`rotation: Quat`) и масштабирование (`scale: Vec3`). Перемножение локальной матрицы на родительскую формирует итоговый `Mat4` глобальной трансформации, который кэшируется в `world.global_transform` и напрямую передается в шейдеры рендерера и модуль коллизий.

## 1.3. Графический конвейер: шейдеры, буферы и типографика

Рендеринг в Oxide вынесен в отдельную подсистему `RenderSystem` (`src/renderer/render_system.rs`), полностью отвязанную от структур мира. `World` не содержит вызовов OpenGL; он хранит только сырые массивы вершин и текстурные дескрипторы.

При вызове `render_system.render_world(ctx, world)` кадр формируется в несколько последовательных фаз:

### 1. Фаза 3D-геометрии (Pipeline3D)
Использует шейдеры OpenGL 4.5 Core:
- Вершинный шейдер: производит трансформацию координат через матрицу `u_mvp = u_projection * u_view * u_model` и вычисляет нормали в мировом пространстве `mat3(transpose(inverse(u_model))) * a_normal`.
- Фрагментный шейдер: реализует классическую модель освещения Blinn-Phong с направленным источником света:

$$I = I_{ambient} + I_{diffuse} \cdot \max(\mathbf{N} \cdot \mathbf{L}, 0) + I_{specular} \cdot \max(\mathbf{N} \cdot \mathbf{H}, 0)^\alpha$$

Для каждого трехмерного объекта создаются и удерживаются GPU-буферы:
- **VAO (Vertex Array Object):** Описывает раскладку атрибутов (положение `vec3`, нормаль `vec3`, UV `vec2`).
- **VBO (Vertex Buffer Object):** Хранит массив байтов вершин.
- **EBO (Element Buffer Object):** Хранит треугольные индексы (`glDrawElements`).

### 2. Фаза 2D-оверлея (Pipeline2D)
Используется для рендеринга плоских элементов интерфейса, фонов и спрайтов. В отличие от 3D, здесь матрица проекции строится через `glam::Mat4::orthographic_rh_gl(0.0, width, height, 0.0, -1.0, 1.0)`, что обеспечивает точное пиксельное позиционирование.

### 3. Текстовый движок (PipelineText & FontAtlas)
Для вывода текста используется связка крейта `fontdue` и специализированного конвейера `PipelineText` (`src/text/pipeline_text.rs`).
1. Шрифт формата TTF или OTF парсится в памяти.
2. При инициализации `FontAtlas` растеризует глифы базовой латиницы и кириллицы в единую монохромную текстуру-атлас размером $512 \times 512$ или $1024 \times 1024$.
3. Каждая строка текста трансформируется в последовательность 2D-квадов с соответствующими UV-координатами атласа и отрисовывается за **один-единственный вызов `glDrawElements`**.

## 1.4. Двухслойный мост: C99 ABI и рантайм на Python

Одна из сильнейших инженерных сторон Oxide — способность компилироваться как в виде статической Rust-библиотеки (`rlib`), так и в виде разделяемой динамической библиотеки (`cdylib`): `oxide.dll` под Windows, `liboxide.so` под Linux и `liboxide.dylib` под macOS.

Вся магия взаимодействия сосредоточена в модуле `src/ffi/mod.rs` (более 48 КБ чистого FFI-кода). Все структуры данных экспортируются с модификатором `#[repr(C)]`:

```rust
#[repr(C)]
pub struct OxideVec3 {
    pub x: f32,
    pub y: f32,
    pub z: f32,
}

#[repr(C)]
pub struct OxideCallbacks {
    pub on_init: Option<extern "C" fn(ctx: *mut OxideContext, user_data: *mut c_void)>,
    pub on_update: Option<extern "C" fn(ctx: *mut OxideContext, dt: f32, user_data: *mut c_void)>,
    pub on_render: Option<extern "C" fn(ctx: *mut OxideContext, user_data: *mut c_void)>,
    pub user_data: *mut c_void,
}
```

### Как устроена обертка на Python (`bindings/python/oxide.py`)?
Вместо громоздких и требовательных к сборке генераторов вроде `pybind11` или `maturin`/`PyO3`, Oxide использует чистый встроенный стандартный модуль **`ctypes`**.

1. При импорте модуля `oxide.py` скрипт находит и загружает скомпилированную `oxide.dll`:
   ```python
   _lib = ctypes.CDLL(dll_path)
   ```
2. Для каждого вызова API определены сигнатуры `argtypes` и `restype`.
3. Пользовательский код на Python выглядит как элегантный объектно-ориентированный скрипт:

```python
from oxide import App, Scene, Vec3, Color, Transform

class Game:
    def on_init(self, ctx):
        self.scene = Scene()
        self.cube = self.scene.spawn_cube_3d(1.0, Transform.from_xyz(0, 1, 0))

    def on_update(self, ctx, dt):
        self.scene.node_rotate_y(self.cube, 1.5 * dt)
        self.scene.update(ctx, dt)

    def on_render(self, ctx):
        ctx.clear(Color(0.1, 0.1, 0.12))
        self.scene.render(ctx)

App("Oxide Game", 1280, 720).run(Game())
```

Когда Python запускает `app.run()`, управление передается в нативный цикл `winit`. Каждый кадр Rust дергает зарегистрированные C-функции обратного вызова, передавая сырой указатель `*mut OxideContext`, а Python-интерпретатор исполняет игровую логику без малейшей потери производительности на стороне нативного OpenGL-рендерера.

# Глава 2: Анатомия компромиссов: честные плюсы и болезненные минусы движка

Ничто не дается даром. При проектировании игровых движков на ранних стадиях разработчики непрерывно балансируют между архитектурной чистотой, производительностью и скоростью доставки фичей. В Oxide этот баланс привел к появлению как выдающихся инженерных находок, так и откровенно болезненных узких мест.

Посмотрим правде в глаза и разберем обе стороны медали.

```

|                                 ТЕХНИЧЕСКИЙ БАЛАНС ОХIDE                                         |
+-------------------------------------------------+-------------------------------------------------+
|                     ПЛЮСЫ                       |                     МИНУСЫ                      |
+-------------------------------------------------+-------------------------------------------------+
| [x] Чистый стек Rust 2021 без C++ легаси       | [!] O(N^2) алгоритм поиска коллизий             |
```

## 2.1. Плюсы и сильные инженерные решения

### 1. Независимый C99 ABI и полная языковая всеядность
Большинство современных движков на Rust (например, Bevy или Fyrox) намертво замыкаются внутри экосистемы Cargo. Вы не можете легко встроить Bevy в приложение на C# или использовать его как встраиваемый вьюпорт в научном Python-пакете. Oxide, напротив, компилируется в самодостаточный динамический модуль со стабильным C-интерфейсом. Это позволяет писать симуляции на C99, C++, Zig, C# или Python, используя единое высокопроизводительное расчетно-графическое ядро.

### 2. Честная математика XPBD для мягких тел и ткани
Один из ярчайших компонентов движка — реализация **Extended Position-Based Dynamics (XPBD)** в `src/physics/pbd_solver.rs`. В отличие от наивных пружинных моделей Гука (Mass-Spring systems), которые взрываются или становятся желеобразными при изменении шага времени $\Delta t$, метод XPBD оперирует концепцией геометрической податливости (compliance) $\alpha$:

$$\Delta \lambda = \frac{-C(\mathbf{x}) - \tilde{\alpha} \lambda}{\nabla C \cdot \mathbf{M}^{-1} \nabla C^T + \tilde{\alpha}}, \quad \text{где } \tilde{\alpha} = \frac{\alpha}{\Delta t^2}$$

Благодаря этому ткань в Oxide сохраняет заданную жесткость независимо от того, работает ли игра при 30 FPS, 60 FPS или 144 FPS.

### 3. Гарантированная защита от висячих ссылок в ECS
Использование `SlotMap` для сущностей и `SecondaryMap` для компонентов гарантирует 100% иммунитет к висячим указателям без необходимости использования сборщика мусора. Если сущность уничтожена в одном системном вызове, все остальные подсистемы корректно проигнорируют устаревший дескриптор.

### 4. Минималистичный след в памяти и мгновенная компиляция
Бинарный файл `oxide.dll` занимает меньше 3 МБ в релизной сборке. Движок не тащит за собой гигабайты рантаймов, запускается за считанные миллисекунды и потребляет в базовом состоянии менее 35 МБ оперативной памяти.

## 2.2. Минусы, узкие места и архитектурные компромиссы

Перейдем к технической критике — тем аспектам кодовой базы, которые разработчику движка обычно неловко показывать на собеседованиях, но которые неизбежно возникают в реальной разработке.

### 1. Квадратичные коллизии $O(N^2)$ без широкой фазы (Broadphase)
Взглянем на реализацию поиска коллизий твердых тел в `src/physics/systems.rs`:

```rust
// Phase 3 & 4: Collision detection & constraint solving
let collider_entities: Vec<EntityId> = world
    .collider
    .keys()
    .filter(|&e| world.is_alive(e))
    .collect();

for i in 0..collider_entities.len() {
    for j in (i + 1)..collider_entities.len() {
        let a = collider_entities[i];
        let b = collider_entities[j];
        // Точная проверка геометрии OBB / Sphere / AABB...
    }
}
```

Здесь полностью отсутствует широкая фаза обнаружения коллизий (Broadphase). Нет пространственного хеширования (Spatial Hashing), нет иерархии ограничивающих объемов (BVH), нет даже простого алгоритма заметания по оси (Sweep-and-Prune).

При 10 объектах движок делает 45 проверок. При 100 объектах — 4 950 проверок. А при 1 000 объектов алгоритм совершает **почти полмиллиона (499 500) геометрических тестов пересечения ориентированных параллелепипедов (OBB SAT)** на каждом тике физики! Это мгновенно ставит процессор на колени при попытке создать даже умеренно плотную сцену.

### 2. Узкое горлышко графики: Draw Call на каждый меш
В `src/renderer/render_system.rs` цикл рендеринга устроен следующим образом:

```rust
for (entity, mesh) in &mut world.mesh_3d {
    // ...
    p3d.draw(ctx.gl, &global, mesh.color, mesh.emissive, None, vao, ebo);
}
```

Каждый трехмерный объект на сцене порождает индивидуальный вызов функции отрисовки `glDrawElements`, сопровождающийся установкой шейдерных uniform-переменных матриц `u_model` и параметров материала.

В движке отсутствует:
- **Geometry Instancing (`glDrawElementsInstanced`):** Отрисовка тысяч одинаковых объектов (например, травы, камней или пуль) за один вызов.
- **Multi-Draw Indirect:** Пакетная отправка команд на GPU.
- **Сортировка по материалам и шейдерам:** Переключения состояний конвейера происходят хаотично в порядке итерации по хеш-таблице.

По этой причине рендерер Oxide упирается в ограничение CPU-to-GPU command submission уже при нескольких сотнях видимых мешей.

### 3. Физическая наивность: скалярный момент инерции вместо тензора
Обратим внимание на вычисление углового ускорения твердого тела в `src/physics/systems.rs`:

```rust
let ang_accel = body.torque_accumulator * body.inv_mass;
body.angular_velocity += ang_accel * dt;
```

Это грубейшее физическое допущение. Во вращательной динамике угловое ускорение $\boldsymbol{\alpha}$ рассчитывается через умножение вектора крутящего момента $\boldsymbol{\tau}$ на **обратный тензор инерции** $\mathbf{I}^{-1}$:

$$\boldsymbol{\alpha} = \mathbf{I}^{-1} \boldsymbol{\tau}$$

Умножение крутящего момента на обычную скалярную массу `inv_mass` означает, что движок считает абсолютно любое тело (будь то тонкий длинный стержень, плоская пластина или асимметричный рычаг) идеальной точечной массой с единичным шаровым распределением плотности. Тела вращаются физически неестественно и не демонстрируют эффектов прецессии или Джанибекова.

### 4. Однопоточный CPU-расчет деформаций и передача данных по PCIe
Физика мягких тел в `src/physics/pbd_solver.rs` рассчитывается исключительно на одном ядре центрального процессора в последовательном цикле. Но главная проблема заключается в последующей доставке данных на видеокарту:

```rust
// Синхронная перезаливка буфера деформированных вершин в GPU
if world.soft_body.contains_key(entity) {
    mesh.update_gpu_buffers(ctx.gl);
}
```

Каждый кадр массив координат вершин деформированной ткани перекачивается из системной оперативной памяти в видеопамять по шине PCIe через блокирующий вызов `glBufferSubData`. При высоком разрешении сетки ткани (например, флаг $64 \times 64$ вершины) это приводит к существенным задержкам на синхронизацию шины данных.

### 5. Темная сторона FFI: `transmute` и сырые указатели
Чтобы обойти строгие правила времени жизни ссылок Rust при передаче контекста рендера в коллбэки C и Python, разработчик применил самый опасный прием в арсенале языка — `std::mem::transmute`:

```rust
// src/ffi/mod.rs
let mut ffi_ctx = OxideContext {
    ctx: unsafe { std::mem::transmute(ctx) },
};
f(&mut ffi_ctx, self.callbacks.user_data);
```

А в модуле разрешения коллизий двух твердых тел `resolve_rigid_body_collision` мы видим обход borrow checker через преобразование ссылок в сырые указатели `*mut Transform`:

```rust
let (Some(trans_a), Some(trans_b)) = (
    world.transform.get_mut(a).map(|t| t as *mut Transform),
    world.transform.get_mut(b).map(|t| t as *mut Transform),
) else { return; };

unsafe {
    // Одновременное мутабельное изменение двух объектов из одной коллекции
    (*trans_a).translation += ...;
    (*trans_b).translation -= ...;
}
```

Хотя логически сущности `a` и `b` гарантированно не равны (`i != j`), компилятор Rust не может доказать раздельность мутабельных ссылок внутри одного контейнера `SecondaryMap`. Применение `unsafe` здесь оправдано архитектурно, однако в случае ошибки в индексации это несет риск неопределенного поведения (Undefined Behavior).

## 3.1. Великий слом: почему сценовое дерево зашло в тупик

В ранних версиях (v0.1.0 – v0.2.3) Oxide проектировался в парадигме объектно-ориентированного дерева сцены, знакомой разработчикам по Unity, Godot или Three.js. Существовал базовый узел `SpatialNode`, который содержал собственный `Transform`, список дочерних узлов `Vec<SpatialNode>` и слабую ссылку на родителя.

Очень скоро эта модель натолкнулась на фундаментальные ограничения модели владения Rust:

1. **Невозможность раздельного заимствования:** Если физическая система хочет обновить положение родительского узла, а система анимации одновременно читает данные дочернего узла, в Rust невозможно получить `&mut Parent` и `&Child`, если родитель владеет ребенком через вектор.
2. **Ад `Rc<RefCell<Node>>`:** Попытка решить проблему через разделяемые указатели с динамической проверкой заимствований привела к лавинообразному разрастанию накладных расходов. Профайлер показал, что проверка счетчиков ссылок и флагов заимствования съедала до 25% времени кадра в пустой сцене!
3. **Утечки памяти при циклических ссылках:** Дочерние узлы удерживали родителей, родители удерживали детей, что приводило к утечкам ресурсов GPU при динамическом спавне и удалении объектов.

В версии **v0.3.0** автор принял радикальное волевое решение: **вырезать старое дерево сцены под корень**. Было удалено более 800 строк и написано свыше 3 400 новых строк за считанные дни.

Архитектура была перестроена на реляционную модель: сущность стала простым 64-битным числом, а отношения родства превратились в две плоские таблицы `parent: SecondaryMap<EntityId, EntityId>` и `children: SecondaryMap<EntityId, Vec<EntityId>>`. Это мгновенно развязало руки borrow checker'у: системы теперь могут безопасно заимствовать таблицу геометрии независимо от таблицы физики или иерархии.

## 3.2. Борьба с лайфтаймами Rust на границе FFI

Вторая сложнейшая инженерная битва развернулась на границе взаимодействия с языком Python.

В Rust ссылки имеют строгий статический жизненный цикл `'a`. Однако при передаче ссылки в C-коллбэк компилятор не может гарантировать, что чужой код не сохранит этот указатель в глобальной переменной и не попытается вызвать его через минуту, когда стек уже уничтожен.

В `FfiAppHandler` возникла дилемма:
- Python-скрипт в методе `on_update(ctx, dt)` должен иметь доступ к методам контекста (`ctx.viewport()`, `ctx.aspect_ratio()`).
- В то же время Python должен иметь возможность вызвать метод сцены `scene.update(ctx, dt)`, который также требует монопольного заимствования `&mut Context`.

Если бы разработчик попытался честно пробросить ссылки через строгие обобщения (generics) и лайфтаймы, компилятор Rust запретил бы любую передачу контекста через границу C-функций.

Решение потребовало создания двухслойной транзитной структуры `OxideContext`:

```rust
pub struct OxideContext<'a> {
    pub(crate) ctx: &'a mut Context<'a>,
}
```

Указатель оборачивается в непрозрачный хэндл, передается в Python, используется во время выполнения коллбэка и аннулируется сразу по возвращении управления в нативный цикл `winit`. Любая попытка закэшировать этот объект на стороне Python и вызвать его вне коллбэка приведет к контролируемой ошибке, защищая нативную память от порчи.

## 3.3. Миграция OpenGL 3.3 -> 4.5 Core Profile в версии v0.3.1

В коммите `18b1826` движок совершил качественный переход с антикварного OpenGL 3.3 (2009 года) на современный стандарт **OpenGL 4.5 Core Profile**.

Эта миграция была вызвана несколькими критическими факторами:
1. **Строгость Glutin 0.32:** Современные версии крейта `glutin` на современных ОС (особенно Windows 11 с новейшими драйверами WDDM 3.0 и macOS под слоем Metal) часто отказывались инициализировать устаревшие legacy-профили OpenGL 3.3 без явных флагов совместимости.
2. **Direct State Access (DSA):** Стандарт 4.5 открыл возможность изменять свойства буферов и текстур без обязательного их предварительного связывания через `glBindBuffer` / `glBindTexture`, что устранило паразитные мутации глобального стейта видеокарты.
3. **Подготовка к Compute Shaders:** Хотя в текущей версии v0.3.1 физика ткани еще считается на CPU, переход на контекст 4.5 заложил аппаратную базу для переноса вычислений в вычислительные шейдеры (Compute Shaders), доступные только начиная с версии OpenGL 4.3+.

## 3.4. Взаимодействие деформируемой ткани и твердого мира

Один из самых сложных физических узлов движка — корректная реакция мягких тел на твердые препятствия.

В `src/physics/pbd_solver.rs` эта задача решена через остроумный математический прием: **проецирование частиц в локальное пространство коллайдера**.

```rust
// Каждая статическая преграда кэширует прямую и обратную матрицу
pub struct StaticColliderInfo {
    pub collider: Collider,
    pub transform: Mat4,
    pub inv_transform: Mat4,
}
```

Когда частица ткани находится в мировой точке $\mathbf{p}_{world}$, наивный тест пересечения с произвольно повернутым в пространстве боксом (OBB) требует сложных тригонометрических расчетов.

В Oxide частица мгновенно переводится в локальные координаты препятствия:

$$\mathbf{p}_{local} = \mathbf{M}_{inv} \cdot \mathbf{p}_{world}$$

В локальном пространстве любой параллелепипед ориентирован строго по осям (AABB). Проверить, находится ли частица внутри, тривиально: достаточно сравнить ее координаты с полуразмерами коллайдера. Если произошло проникновение, частица проецируется на ближайшую грань, а затем результат возвращается в мировой базис умножением на прямую матрицу трансформации $\mathbf{M}$.

Этот алгоритм позволил добиться абсолютно стабильной симуляции ткани, драпирующейся на твердые сферы и кубы, избежав при этом вычислительного коллапса.

## 3.5. Дорожная карта: куда Oxide будет двигаться дальше?

Oxide уже доказал жизнеспособность своей концепции: на нем успешно работают демонстрационные 3D-игры с физикой и симуляторы ткани, управляемые из Python. Но чтобы превратиться из амбициозного эксперимента в индустриальный инструмент, движку предстоит решить ключевые врожденные проблемы:

1. **Внедрение широкой фазы коллизий (Dynamic AABB Tree / BVH):**
   Замена квадратичного алгоритма $O(N^2)$ на иерархическое дерево ограничивающих параллелепипедов снизит сложность поиска столкновений до $O(N \log N)$, позволив симулировать тысячи твердых тел одновременно.
2. **Полноценный тензор инерции для RigidBody:**
   Внедрение матрицы $3 \times 3$ тензора инерции для боксов, сфер и капсул для достижения физически достоверной динамики вращения.
3. **GPU Compute Shaders для XPBD:**
   Перенос расчетного ядра деформации ткани из CPU в вычислительные шейдеры OpenGL 4.5. Это позволит рассчитывать миллионы частиц в реальном времени параллельно на тысячах потоковых процессоров видеокарты.
4. **Инстансинг геометрии (`glDrawElementsInstanced`):**
   Объединение однотипных мешей в пакеты для радикального снижения нагрузки на CPU.
5. **Долгосрочная перспектива: WGPU / Vulkan:**
   Постепенный переход от монопольного OpenGL к современной спецификации WebGPU (через крейт `wgpu`), что откроет путь к работе движка в браузере (WebAssembly) и на мобильных платформах.

# Заключение

**Oxide** — это яркий памятник тому, как амбициозная инженерная мысль преодолевает сопротивление компилятора, математики и железа. Он полон смелых решений (чистый C99 ABI, отказ от C++ зависимостей, XPBD на Rust) и в то же время несет на себе шрамы неизбежных компромиссов (наивные коллизии, отсутствие инстансинга, сырые FFI-указатели).

Но именно в этом заключается настоящая инженерия: не строить идеальные абстрактные замки в вакууме, а писать рабочий код, честно признавать его слабые места и непрерывно двигать его вперед.
